# OP-02 — ممیزی زنجیره ارتقا و سیاست نسخه VazinCMS

**وضعیت:** `CANDIDATE / NO-GO` — این سند و ابزار همراه به هیچ عنوان مجوز Deploy، تغییر دیتابیس یا انتشار نیستند.

## مسئله تأییدشده در ۱۰ اکتبر ۲۰۲۶

در آرشیوهای تاریخی مشاهده‌شده، Installerها زنجیره یک‌مرحله‌ای زیر را ثبت می‌کنند:

`10.29.0 → 10.30.0 → 10.30.1 → 10.30.2`

هر چهار درخت تاریخی از نظر فایل‌های **مندرج در Manifest همان نسخه** سالم بودند؛ اما این به معنی امضا یا تأیید منشأ آنها نیست. کانال عمومی پایدار اکنون `10.30.2` را ارائه می‌کند و فایل‌های بسته/امضا/checksum نسخه‌های واسطه با نام‌های مورد بررسی در مسیر رسمی، 404 پاسخ می‌دهند.

تناقض حیاتی: `deploy/install.sh` در نسخه `10.30.2` مقدار `OLD_VERSION='10.30.1'` دارد، اما `vazin-package.json` همان نسخه فهرست `supported_current_versions=['10.30.0']` را اعلام می‌کند. مقدار `minimum_current_version=10.30.0` به‌تنهایی مجوز رد شدن از نسخه واسطه نیست. **فهرست صریح نسخه‌های مبدأ، Installer و مسیر ارتقای داده باید هماهنگ باشند.**

در سه نصب مدیریت‌شده با فایل `VERSION=10.29.0`، وضعیت اجرای Migration یکسان نبود: در یک نصب `10.30.0` از قبل ثبت شده بود و در دو نصب دیگر خیر. نباید نسخهٔ فایل را به‌جای وضعیت schema گرفت یا migration را صرفاً از روی رقم نسخه دوباره اجرا کرد.

## ابزار ممیزی فقط‌خواندنی

`scripts/upgrade_path_audit.py` فقط یک زنجیره را از روی **دایرکتوری‌های محلی مستقل** مشاهده می‌کند:

```bash
python3 scripts/upgrade_path_audit.py \
  --start 10.29.0 --target 10.30.2 \
  --release 10.29.0=/STAGING/10.29.0 \
  --release 10.30.0=/STAGING/10.30.0 \
  --release 10.30.1=/STAGING/10.30.1 \
  --release 10.30.2=/STAGING/10.30.2
```

مسیرهای نمونه بالا واقعی نیستند؛ فایل‌های خصوصی سیستم و credential را در مخزن، Issue یا گزارش عمومی قرار ندهید. ابزار نصب، اجرای SQL، فراخوانی شبکه یا نوشتن روی سیستم ندارد. ورودی آن نباید به مسیر Production اشاره کند مگر در چارچوب ممیزی فقط‌خواندنی با مجوز عملیاتی.

این ابزار نسخه مورد انتظار، تطبیق `VERSION` و `vazin-package.json`، رابطه `OLD_VERSION` و `NEW_VERSION`، فهرست نسخه‌های مبدأ، مانفیست و هش فایل‌های آن، برابری موجودی migrationهای SQLite/PostgreSQL و عدم حذف/تغییر migrationهای تاریخی را کنترل می‌کند.

خروجی JSON شامل `chain_contract=PASS/FAIL` و **همیشه** `release_decision=NO_GO` است؛ کد خروج همیشه `70` است. حتی `chain_contract=PASS` به معنای تأیید بسته امضاشده، هویت ناشر، مسیر سالم دیتابیس، انتشار، یا مجوز `main` نیست. برای تست ابزار:

```bash
python3 -m unittest discover -s tests -p 'test_upgrade_path_audit.py' -v
```

## شروط لازم پیش از پذیرش OP-02

1. تهیه بسته‌های immutable و قابل‌دریافت هر مرحله واسطه، با امضای معتبر ناشر و checksum مستقل؛ یا طراحی یک بسته جهشی جدید با زنجیره migration و rollback مستقل که به‌صورت کامل در Staging آزمایش شود. فایل‌های تاریخی محلی را به‌طور ضمنی بسته رسمی و امضاشده قلمداد نکنید.
2. اصلاح تناقض Package/Installer **در انتشار جدید با نسخه و امضای جدید**؛ بسته رسمی امضاشده `10.30.2` را بی‌سروصدا تغییر ندهید، چون زنجیره اعتماد می‌شکند.
3. بررسی نسخه واقعی، schema migrations، runtime و backup هر نصب جداگانه. Migrationهای اعمال‌شده جلوتر از VERSION نیازمند reconcile با شواهد هستند.
4. تمرین ارتقای تک‌مرحله‌ای و برگشت کد و داده روی نسخه کپی در Staging، شامل SQLite و PostgreSQL و تست‌های application/health؛ مجوز یک نصب به نصب دیگر تعمیم داده نشود.
5. بازبینی `stable.json` و کانال‌های stable/canary، اثبات بارگذاری بسته مقصد، سیاست حمایت از نسخه‌های قبلی، پلن عدم دسترسی، و کنترل ظرفیت بازگشت.
6. تصویب انسانی نسخه هدف، اثرانگشت بسته‌ها، سیاست release، RPO/RTO و زمان مناسب rollout؛ ثبت رسید قابل راستی‌آزمایی. تنها پس از عبور کامل این کنترل‌ها می‌توان گیت Production را جداگانه ارزیابی کرد.

**مرز کار:** اتصال Travel/Visa ↔ VazinPay یک workstream مستقل است؛ هیچ فعال‌سازی فروش یا دستکاری Vazin Accounting برای این ممیزی مجاز نیست.
