# OP-02.13 — آزمایش ایزولهٔ کنترل نوشتن، نسل اجرا و ترتیب بستن Barrier در PHP-FPM

**تاریخ: ۱۵ اکتبر ۲۰۲۶ | محدوده: فقط دو PHP-FPM مصنوعی | وضعیت: DRAFT / Production NO-GO**

## مسئله و خطای نشان‌داده‌شده

در OP-02.3 نشان داده شد پاسخ HTTP 503 به درخواست تازه به‌معنی تمام‌شدن درخواست‌های قدیمی یا بسته‌بودن تمام مسیرهای نوشتن نیست. ممیزی OP-02.12 نشان داد Travel و Visa در پیکربندی فعلی S17 از Backend عمومی مشترک PHP 8.5 استفاده می‌کنند و شواهد معتبر **per-site** دربارهٔ Drain درخواست‌ها و توقف Writerها وجود ندارد.

در OP-02.13 هیچ تغییر یا آزمایش مخربی روی این سرویس‌های واقعی انجام نشده است. فقط یک نمونهٔ مصنوعی قابل بازتولید با دو Master مستقل PHP-FPM 8.5 و دو Unix socket تازه در دایرکتوری موقت حافظه روی S17 ساخته شد. همهٔ اسکریپت‌های PHP و فایل‌های نشانه صرفاً آزمایشی‌اند.

## قرارداد Barrier مصنوعی

این نمونه **طراحی توصیه‌شده برای Production نیست** و نباید آن را روی سایت واقعی کپی کرد. فقط یک جهش سادهٔ مدل را می‌آزماید.

- وضعیت هر سایت در فایل root-owned با مجوز ثابت 0644، یعنی خواندنی ولی نه قابل‌تغییر برای Worker آزمایشی، قرار می‌گیرد: OPEN:g1، CLOSED:g1، سپس OPEN:g2 و OPEN:g3.
- Coordinator آزمایشی با flock انحصاری روی همان فایل، وضعیت را به CLOSED:gN تغییر می‌دهد و بعد از flush/fsync قفل را آزاد می‌کند. مقدار قدیم، مالکیت/نوع فایل، نبودن symlink و hardlink و افزایش دقیق یک نسل تأیید می‌شوند.
- اسکریپت PHP در **نقطهٔ واحد نوشتن فایل نشانه** قفل انحصاری همان Barrier را می‌گیرد؛ در صورت نبودن فایل/قفل، CLOSED بودن یا نابرابری نسل درخواست و نسل فعلی، HTTP 503 و عدم نوشتن نتیجه می‌دهد. در صورت تطبیق، نوشتن پیش از آزادکردن قفل انجام می‌شود.
- این قفل فقط یک file_put_contents مصنوعی را پوشش می‌دهد؛ Database/Redis/Session/Queue/Cron/Webhook/Payment/External API، همهٔ فراخوانی‌های واقعی PHP، و عملیات چندمرحله‌ای پوشش داده نشده‌اند.
- هیچ Token واقعی، گواهی، DNS، Nginx Production، PHP-FPM زنده، دیتابیس، دادهٔ مشتری یا پورت TCP در آزمایش خوانده یا تغییر داده نشده است.

## نتایج اجرای واقعی روی S17

اسکریپت اختیاری: python3 tests/integration/isolated_fpm_site_write_barrier_rehearsal.py

| مورد | مشاهدهٔ آزمایشگاهی |
|---|---|
| درخواست قدیمی عمداً بدون Guard بعد از CLOSED:g1 | نوشتن انجام شد؛ **ضعف کنترل‌نشده بازتولید شد** |
| بستن Travel هنگام درحال‌اجرا بودن درخواست g2 | درخواست از پیش شروع شده بود؛ Barrier بسته شد |
| درخواست جدید g2 هنگام بسته‌بودن Travel | HTTP 503، نشانه نوشته نشد |
| درخواست Visa با Master و Barrier مستقل هنگام بسته‌بودن Travel | HTTP 200، نوشتن موفق |
| درخواست قدیمی g2 پس از بازشدن نسل g3 | HTTP 503، نوشتن انجام نشد |
| درخواست g3 با نسل جاری باز | HTTP 200، نوشتن نشانه انجام شد |
| نوشتن محافظت‌شدهٔ g3 که قفل را از پیش داشت | ابتدا نوشتن کامل شد، **سپس** بستن Barrier پاسخ داد |
| نوشتن g3 بعد از تکمیل CLOSE | HTTP 503، بدون نشانهٔ جدید |
| نبودن فایل Barrier آزمایشی | HTTP 503، Fail-Closed |

**۹ سناریوی مستقل، exit 0.** واژهٔ PASS در سناریوی ناامن به معنی «آسیب‌پذیری ساختگی با نتیجهٔ مورد انتظار رخ داد» است، نه تأیید امنیت آن. نوشتن بعد از CLOSE در برنامهٔ بدون Guard یک NEGATIVE CONTROL است.

نمونهٔ قفل مشترک و بررسی نسل در کنار یک فایل‌نویسی، تضمین نمی‌کنند که VazinCMS واقعی چنین کنترلی در تمامی مسیرهای نوشتن دارد.

## آزمون‌های کد و ایمنی

- فایل تست در tests/integration/ اختیاری است؛ Release Check فقط unit tests غیرعملیاتی را اجرا می‌کند.
- دو PHP-FPM تنها با --nodaemonize و --fpm-config از configهای موقت زیر /dev/shm ساخته می‌شوند؛ همهٔ socketها Unix، مستقل و مصنوعی‌اند. فقط پردازش‌های همین آزمایش در پایان متوقف می‌شوند.
- Test harness خطای راه‌اندازی، توالی نسل، وضعیت قفل، درخواست قدیمی/جدید و پاک‌سازی پردازش‌های آزمایشی را fail-closed کنترل می‌کند.
- واحدهای tests/test_isolated_fpm_site_write_barrier.py، ماشین حالات، قفل، رد symlink/hardlink، رد فایل world-writable، عدم ارث‌بری متغیر محیطی CGI و محدودیت‌های نمونهٔ PHP را بررسی می‌کنند.

## چرا Production همچنان NO-GO است؟

این آزمایش **صرفاً محافظت از یک نقطهٔ نوشتنِ نمونه** را می‌سنجد؛ «Worker Drain واقعی» و توقف cron/queue/background job را اثبات نمی‌کند. فیلدهای نهایی live_per_site_drain_verified=false، live_queue_or_cron_writers_verified=false، php_db_external_side_effects_covered=false، release_authorized=false و production=NO_GO باقی می‌مانند.

برای استفادهٔ عملیاتی، فایل+flock کافی نیست. مالک و بازبینان باید ابتدا همهٔ side effectها را بشناسند، سیاست تراکنشی/epoch fencing برای DB، session، queue، webhook و عملیات خارجی را تعریف کنند، هماهنگی اتمیک بین پذیرش درخواست، نوشتن و Swap را بیازمایند، Writerهای غیر PHP-FPM را کنترل، هویت tenant را بررسی و سیاست Rollback/DR، RPO/RTO، OPcache، پرداخت و OAuth را تأیید کنند. از شمار Worker یا پاسخ عمومی 503 نباید رسید «Drain=0» صادر کرد.

**نتیجه: آزمایش دو Pool مصنوعی موفق؛ Production همچنان NO-GO است.**
