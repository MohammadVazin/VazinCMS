# OP-02.3 — ممیزی فقط‌خواندنی درخواست‌های درحال‌اجرا و Poolهای PHP-FPM

**وضعیت: CANDIDATE / NO-GO**. این سند و ابزار نه مجوز نصب یا Rollback هستند و نه دستور تغییر تنظیمات زنده.

## مسئله‌ای که در آزمون واقعی پیدا شد

در یک آزمایش با Nginx و PHP-FPM مستقل، یک درخواست PHP قبل از فعال‌شدن Maintenance آغاز شد. پس از Reload کنترل‌شدهٔ Nginx آزمایشی، درخواست‌های جدید HTTP 503 گرفتند، اما درخواست قدیمی **پس از فعال‌شدن Fence همچنان در فایل آزمایشی نوشت** و HTTP 200 تمام شد. بنابراین Fence و Health موفق سایت، تخلیهٔ درخواست‌های قدیمی را ثابت نمی‌کنند.

این مسئله مخصوصاً در Pool مشترک PHP-FPM مهم است: حتی اگر مسیرهای عمومی یک سایت مسدود شوند، پردازشگرهای قدیمی آن سایت و Jobهای پس‌زمینه ممکن است هنوز به دیتابیس مشترک یا فایل‌ها بنویسند.

## ابزار ممیزی اولیه

نمونهٔ اجرا، صرفاً خواندنی:

    python3 scripts/fpm_drain_inventory.py \
      --hosts travel.vazin.online visa.vazin.online studio.vazin.online

ابزار متن بلوک‌های server در فایل‌های Nginx و گزینه‌های Poolهای PHP-FPM را می‌خواند؛ **به سوکت PHP-FPM وصل نمی‌شود** و هیچ فایل، Nginx، Job، دیتابیس یا DNS را تغییر نمی‌دهد. خروجی JSON برای هر میزبان شامل upstream، Pool متناظر، شمار میزبان‌های مشاهده‌شدهٔ مرتبط با upstream، وجود مسیر status و شکاف شواهد است.

شمار میزبان‌ها یک **مشاهدهٔ ایستا و تقریبی** است، نه شمار سایت‌های فعال. خواندن includeهای Nginx، تنظیمات تولیدشده در runtime، درخواست‌های FPM، cronها و صف‌ها هنوز در این نسخه انجام نمی‌شود. به همین دلیل فیلدهای drain_verified و release_authorized همواره false، تصمیم NO_GO و کد خروج **۷۰** هستند؛ حتی وقتی Pool اختصاصی باشد و pm.status_path تنظیم شده باشد.

هیچ کلید، رمز، متن فایل .env یا کل تنظیمات خصوصی سرور در خروجی این ابزار نمایش داده نمی‌شود.

## شواهد خواندنی S17 در ۱۰ اکتبر ۲۰۲۶

پس از اصلاح روش شمارش که اکنون هر بلوک server را به‌صورت مستقل بررسی می‌کند:

- **Travel و Visa** از unix:/run/php/php8.5-fpm.sock با Pool عمومی www استفاده می‌کنند.
- این upstream در بررسی ایستای تنظیمات روی **۱۶ نام میزبان** دیده شد؛ برآورد اولیهٔ ۱۷ مورد ناشی از یکی‌انگاشتن بلوک‌های متعدد یک فایل بود و ملاک نیست.
- **Studio** از unix:/run/php/vazincms-studio.sock با Pool اختصاصی استفاده می‌کند.
- برای این Poolهای بررسی‌شده، نه pm.status_path و نه pm.status_listen پیکربندی‌شده مشاهده شد.
- ابزار وضعیت لحظه‌ای Workerها، درخواست‌های قدیمی یا Jobهای پس‌زمینه را نمی‌خواند؛ عدم مشاهده، اثبات صفر بودن نیست.

## پیش‌نیازهای پذیرش واقعی Drain

1. بررسی Nginx موثر و تمام مسیرهای عمومی، Asset، Webhook، API و درخواست‌های نگارنده؛ Fence باید **تمام آن‌ها** را پوشش دهد، نه صرفاً /health.
2. جداسازی Pool اختصاصی هر سایت یا تله‌متری قابل‌انتساب به همان سایت؛ Pool عمومی مشترک اجازه نسبت‌دادن Workerها به Travel و Visa را نمی‌دهد.
3. اعمال Fence، جلوگیری از ایجاد درخواست و Job جدید، و **مشاهدهٔ مستقل اتمام تمام درخواست‌های قبلی** همراه با بازهٔ پایداری معتبر و شواهد قابل‌ممیزی.
4. کنترل وضعیت Writerها و Jobهای پس‌زمینه (از جمله Cron/Queue)، اتصال دیتابیس و قفل‌ها؛ صرف یک sleep ثابت یا فایل JSON ساختگی قابل قبول نیست.
5. بررسی Pool status از مسیر امن جداگانه، بدون نمایش اطلاعات حساس؛ status به‌تنهایی گواهی Drain نیست.
6. تست درخواست طولانی، شکست Worker، قطع اتصال و بازگشت نسخه در Staging چندمستاجری؛ پایش هم‌زمان Health سایت‌های همسایه.
7. تأیید مالک، امضای بسته، درستی بکاپ/بازیابی و شرایط RPO/RTO پیش از هر انتشار.

**تا کامل‌شدن این شروط، اجرای Installer نامزد روی S17 ممنوع و Production Release Gate برابر NO-GO است.**
